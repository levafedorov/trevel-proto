# MVP: хардкод контента (без CMS пока)

> Решение по этапу. CMS (Storyblok) — позже; расширяем всё, когда будет готов UX/UI.

## Решение

Для MVP текст туров **хардкодим в коде**, CMS пока не подключаем.

**Почему сейчас это правильно:**
- Один реальный тур, контент вносит разработчик — CMS решает задачу («мама редактирует
  сама»), которой пока нет.
- Storyblok добавляет настройку (HTTPS-локалхост, токены, схема, деплой) ради
  отсутствующей потребности — преждевременная сложность.
- Хардкод = быстрее до рабочего MVP.

Полный разбор по CMS и бесплатному тарифу — в истории обсуждения (Storyblok: 1 seat
бесплатно, MCP-сервер официальный, тестирование через draft + Visual Editor на
`https://localhost:3000`). Триггер вернуться к CMS — когда маме нужен **свой** логин
для самостоятельного редактирования.

## Правила, чтобы переезд на CMS был безболезненным

Хардкодить нужно **правильно** — так, чтобы миграция свелась к замене источника данных,
а не к переписыванию вёрстки.

1. **Данные отдельно от вёрстки.** Весь контент тура — в `app/composables/useOffers.ts`
   (единый источник, там уже лежат моковые туры), а не строками по компонентам.
   Миграция потом = заменить этот источник на `fetch` из CMS; компоненты не трогаем.

2. **Форма данных = доменная модель** (`domain-model.drawio`). Даже захардкоженный объект
   должен иметь ту же структуру, что отдаст CMS: `itinerary[]` (дни с таймингом,
   локациями, питанием), `departures[]` (заезды с датами и местами),
   `inclusions[]`/exclusions, `paymentOptions[]`, `practicalInfo[]`. Иначе при переезде
   придётся переделывать и типы, и вёрстку.

3. **Двуязычие RU/EN** — по той же схеме, что уже в проекте (i18n). Тексты контента тура
   ведём парой ключей/полей, чтобы CMS-локали легли без переделки.

## Что конкретно предстоит (когда договоримся делать)

- Расширить тип `TouristicOffer` в `useOffers.ts` под доменную модель — сейчас он
  **плоский** (нет программы по дням, заездов, инклюжнов).
- Завести первый реальный тур из Word-документа «Жемчужины Эгейского побережья»
  (7 дней, 19–25.09.2026, 1000 €) в эту структуру, пока с плейсхолдер-фото.
- Секции Версии A (`OfferHero`, `OfferItinerary`, ...) рендерят страницу из этих данных —
  **после готовности UX/UI**.

## План расширения (порядок)

1. **Сейчас (MVP):** расширить модель данных + завести первый тур (данные, migration-safe).
2. **После UX/UI:** сверстать секции Версии A по макету + мобильная спека
   (`version-a-mobile.md`).
3. **Когда нужно самостоятельное редактирование:** миграция источника данных на Storyblok
   (замена `useOffers` на fetch), контент-модель по `domain-model.drawio`.
